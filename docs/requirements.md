# Requirements

## Purpose

Java, JavaScript, Python 소스 코드를 대상으로 정적 애플리케이션 보안 테스트를 수행하고, 진단 결과를 저장·조회·관리한다.

## Functional Requirements

- `@company.com` 사내 이메일 계정 로그인·로그아웃
- SUPER_ADMIN / PROJECT_MANAGER / USER 역할 구분 및 모든 기능에 일관된 역할 정책 적용
- SUPER_ADMIN 사용자 계정 생성·수정
- SUPER_ADMIN 사용자 역할 변경
- SUPER_ADMIN 사용자 활성화·비활성화
- SUPER_ADMIN이 지정한 초기 비밀번호와 신규 사용자의 최초 개인 비밀번호 변경
- 로그인 사용자의 현재 비밀번호 확인 기반 본인 비밀번호 변경
- 사용자 계정은 물리 삭제하지 않는다.
- 프로젝트 생성·수정·조회
- 프로젝트별 사용자 권한 관리
- SUPER_ADMIN 또는 할당된 PROJECT_MANAGER의 ZIP 소스 업로드
- ZIP 업로드별 최신 소스 버전, 배포 버전과 설명 입력 및 분석 시점 스냅샷 보존
- 안전한 압축 해제 후 최신 ZIP의 파일명·업로드 시각·파일 수·전체 크기·감지 언어·주요 상대경로를 분석 전에 확인
- 중앙 language registry 기반 Java, JavaScript, Python 언어 식별 및 확장 구조
- 프로젝트별 단일 언어 또는 ZIP에서 감지된 Java, JavaScript, Python 통합 분석 모드
- SUPER_ADMIN 또는 할당된 PROJECT_MANAGER의 Semgrep 기반 분석 실행
- 분석 상태 관리: PENDING, RUNNING, COMPLETED, FAILED
- 분석 결과 정규화 및 저장
- 분석별 소스 SHA-256, 소스 스냅샷, Semgrep 버전, 규칙 세트 SHA-256, 활성 규칙 목록·SHA-256 기록
- 파일 경로와 코드 위치를 포함한 Finding 조회
- severity, confidence, rule 정보 제공
- Finding 상세 조회 및 severity 필터
- Finding 조치 상태·검토 의견·상태 변경 계정·변경 시각 관리
- Finding 조치 담당자·조치 기한 관리와 기한 초과 조회
- 최신 소스 기반 Finding 재검증과 여전히 탐지됨·해결 추정·확인 필요 이력 조회
- 분석 이력과 상세에서 분석 실행 계정 조회
- 분석 실행 단위 CSV 상세 보고서와 PDF 고객 보고서 다운로드
- KISA 소프트웨어 개발보안 49개 항목 카탈로그 관리
- 항목별 구현 상태와 지원 언어 관리
- Python, Java, JavaScript에서 공통 KISA 진단 항목 9개를 언어별 Semgrep 규칙으로 지원하고, 신뢰할 수 없는 데이터의 역직렬화는 Java와 Python에서 추가 지원
- SFR-012: 신규 Semgrep YAML은 개발자가 규칙 디렉터리에 배치하고, SUPER_ADMIN은 `/rules/new`에서 기존 KISA 카탈로그 항목에 언어별 Semgrep Rule ID를 등록·수정한다. 웹 애플리케이션은 YAML 내용을 해석하거나 편집하지 않으며 공식 카탈로그 식별자와 명칭도 변경하지 않는다.
- SFR-013: 인증된 모든 역할은 KISA 49개 카탈로그를 검색·필터·상세 조회할 수 있고, SUPER_ADMIN에게만 규칙 관리 기능을 표시한다.

## Data Requirements

- DAR-001: 관계형 데이터베이스의 트랜잭션·무결성을 사용하고 스키마 변경 이력을 관리한다.
- DAR-002: 사용자 식별자, 비밀번호 검증 정보, 역할, 활성 상태, 최초 비밀번호 변경 필요 여부, 생성·수정 시각을 저장한다.
- DAR-003: 프로젝트명, 설명, 소스 유형, 기준 분석 언어, 다중 언어 분석 여부, 소스 위치, 생성자, 생성·수정 시각을 저장한다.
- DAR-004: 프로젝트와 사용자의 접근 관계를 별도 데이터로 관리한다.
- DAR-005: 프로젝트, 엔진, 언어, 상태, 실행자, 시작·종료 시각, 오류, 실행 요약을 분석별로 저장한다.
- DAR-006: 분석 실행, 진단 항목, 기준 ID, 언어, 심각도, 신뢰도, 위치, 메시지, 근거, 권고, 원본 결과를 Finding에 저장한다.
- DAR-007: 진단 기준의 식별자, 명칭, 설명, 기준 ID, 분류, 항목 번호, 참조 정보, 활성 여부, 기본 심각도를 관리한다.
- DAR-008: Finding에 분석 시점의 진단 항목명, 기준, 언어, 심각도, 신뢰도를 보존한다.
- DAR-009: 분석 요약과 원본 결과를 조회 가능한 JSON으로 저장한다.
- DAR-010: 사용자-프로젝트-분석 실행-Finding-Rule 관계의 FK 무결성을 보장한다.
- DAR-011: Finding의 최신 조치 상태, 의견, 변경 계정과 변경 시각을 별도 1:1 데이터로 저장한다.
- DAR-012: 프로젝트의 최신 ZIP 소스 버전·배포 버전·설명을 저장하고 분석 실행 요약에는 실행 시점 값을 보존한다.
- DAR-013: Finding의 최신 담당자와 조치 기한을 조치 상태 데이터에 저장하고 담당자는 프로젝트 할당 관계를 만족해야 한다.
- DAR-014: 재검증의 원본 Finding, 새 분석 실행, 일치 Finding, 비교 결과, 실행 계정과 실행 시각을 이력으로 저장한다.
- DAR-015: 프로젝트의 최신 ZIP에 대해 안전한 압축 해제 결과로 계산한 제한된 소스 요약을 JSON으로 저장한다.

## Security Requirements

- SEC-001: 비밀번호는 평문으로 저장하거나 응답에 노출하지 않고 검증된 단방향 해시로 보호한다.
- SEC-002: 인증이 필요한 기능은 유효한 인증 정보가 없는 요청을 차단하고 인증 정보의 발급·검증·만료 정책을 적용한다.
- SEC-003: 계정·역할·규칙 관리와 프로젝트 생성은 SUPER_ADMIN으로 제한한다. 프로젝트 수정·사용자 배정·소스 업로드·분석 실행 및 분석 오류 원문 조회는 SUPER_ADMIN 또는 해당 프로젝트에 할당된 PROJECT_MANAGER로 제한한다.
- SEC-004: USER는 할당된 프로젝트의 분석 이력과 Finding만 읽기 전용으로 조회하고 생성·수정·권한 변경·분석 실행은 제한한다. 미할당 PROJECT_MANAGER도 프로젝트 자원에 접근할 수 없다.
- SEC-005: 분석 실행 및 결과 조회는 요청 ID만 신뢰하지 않고 DB의 프로젝트 관계와 사용자 권한으로 검증한다.
- SEC-006: 권한 없는 프로젝트·분석 실행·Finding 요청은 자원 존재 여부가 드러나지 않도록 `404`로 처리한다.
- SEC-007: 저장된 소스는 프로젝트별 경계 안에 두고 분석 실행마다 별도 작업 디렉터리로 복사하여 격리한다.
- SEC-008: 업로드·압축 해제·소스 접근에서 ZIP Slip, 절대 경로, 경로 탈출, 심볼릭 링크, 특수 파일 및 암호화 ZIP을 거부한다.
- SEC-009: 업로드·압축 해제·대상 파일·Semgrep 동시 작업·메모리·출력·실행 시간을 제한하고, timeout 시 전체 프로세스 그룹을 종료하며 오류 원문은 SUPER_ADMIN과 해당 프로젝트의 PROJECT_MANAGER만 조회한다.
- SEC-010: 외부 구성요소의 버전을 고정하고 취약점 점검, 라이선스 검토 및 보안 업데이트 절차를 운영한다.
- SEC-011: Finding 조치 상태 변경은 SUPER_ADMIN 또는 해당 프로젝트에 할당된 PROJECT_MANAGER로 제한하고 USER는 읽기 전용으로 조회한다.
- SEC-012: 보고서는 프로젝트 접근 관계를 확인한 사용자에게만 제공하고 원본 Semgrep JSON, 내부 오류, 시스템 절대경로 및 스프레드시트 실행 가능 수식을 포함하지 않는다.
- SEC-013: Finding 담당자와 조치 기한 변경은 SUPER_ADMIN 또는 해당 프로젝트에 할당된 PROJECT_MANAGER로 제한하고, 프로젝트에 할당된 활성 사용자만 담당자로 지정한다.
- SEC-014: Finding 재검증 실행은 SUPER_ADMIN 또는 해당 프로젝트에 할당된 PROJECT_MANAGER로 제한하고 USER는 재검증 이력을 읽기 전용으로 조회한다.
- SEC-015: 소스 요약은 ZIP 전체 검증 후 실제 정규 파일만 사용해 계산하고 파일 내용·시스템 절대경로를 저장하거나 표시하지 않는다.

최초 최고 관리자 계정은 `admin@company.com` / `admin`이며 비밀번호는 bcrypt 해시로만 저장한다. 최고 관리자는 자기 자신과 마지막 활성 SUPER_ADMIN을 비활성화하거나 다른 역할로 변경할 수 없다. SUPER_ADMIN이 UI에서 생성한 신규 사용자는 개인 비밀번호를 변경하기 전까지 비밀번호 변경과 로그아웃 외의 보호 기능을 사용할 수 없다. 로그인·로그아웃을 포함한 상태 변경 요청은 CSRF 토큰으로 보호한다. 구체적인 인증, 제한값 및 외부 구성요소 정책은 `configuration.md`와 `security.md`를 따른다.

## Test Requirements

- TST-001: 세 역할의 로그인, 인증 쿠키 발급, 신규 계정 최초 비밀번호 변경 강제, 본인 비밀번호 변경 및 미인증 보호 기능 접근 차단을 검증한다.
- TST-002: SUPER_ADMIN의 전체 관리, 할당된 PROJECT_MANAGER의 프로젝트 운영, USER의 읽기 전용 제한을 검증한다.
- TST-003: 프로젝트 사용자 할당 후 조회 가능 여부와 미할당 프로젝트의 분석 결과 조회 제한을 검증한다.
- TST-004: ZIP 소스 수집, 분석 대상 언어 식별, Semgrep 코드 구조 분석, 진단 규칙 실행 및 Finding 표준화 흐름을 검증한다.
- TST-005: 지원 언어별 취약·정상 소스와 고정된 기대 결과로 구현된 진단 항목의 탐지 여부, 파일·줄 위치 및 메타데이터를 검증한다.
- TST-006: KISA 49개 항목 모두에 식별자, 분류, 항목 번호, 명칭 및 구현 상태가 저장되는지 검증한다.
- TST-007: 분석 상태, Finding 저장, 심각도·신뢰도·조치 상태·담당자·기한 초과 필터, 상세 조회 및 Rule 연결을 검증한다.
- TST-008: 유효하지 않은 분석 대상과 실행 오류의 FAILED 상태·안전한 오류 정보, 원인 수정 후 재실행 및 이전 실패 이력 보존을 검증한다.
- TST-009: 재검증의 동일 위치 재탐지·위치 변경·미탐지·분석 실패 비교와 실행 권한, 이력 보존 및 조치 상태 불변을 검증한다.
- TST-010: 안전한 ZIP의 실제 소스 요약 저장·조회, 상대경로·언어 감지·표시 제한과 실패한 교체 시 기존 요약 보존을 검증한다.

시험 데이터, 기대 결과 및 TST별 자동·수동 검증 절차는 `testing.md`를 따른다.

## Quality Requirements

- QLT-001: 인증·권한, 프로젝트 관리, 데이터 관리, 분석 처리, 진단 항목 및 결과 관리 기능을 책임별 모듈로 분리하여 유지보수성을 확보한다.
- QLT-002: 개별 진단 항목을 독립적으로 추가·수정·시험할 수 있게 구성하고 변경 영향 범위를 최소화한다.
- QLT-003: 공통 분석 흐름과 결과 모델을 유지하면서 추가 언어와 진단 기준을 수용할 수 있어야 한다.
- QLT-004: 분석 방식이나 규칙 구현 차이와 관계없이 파일 위치, 심각도, 신뢰도, 근거를 포함한 공통 결과 형식으로 제공한다.
- QLT-005: 프로젝트, 분석 실행, Finding, Rule 관계와 분석 대상 언어의 정합성을 저장·조회 시 유지한다.

모듈 소유권, 확장 절차, 공통 결과 계약 및 정합성 불변조건은 `quality.md`를 따른다.

## Dependency Versioning

이 문서는 제품의 기능 요구사항을 정의한다.

설치할 Python 패키지와 정확한 버전은 Phase 1에서 생성하는 프로젝트 루트의 `requirements.txt`에 고정한다.

Python 실행 버전은 3.12를 기준으로 한다. Semgrep 버전도 `requirements.txt`에서 고정한다.

## Completion Criteria

각 요구사항에 대해 구현 위치와 검증 방법이 존재해야 한다. 핵심 사용자 흐름은 자동 테스트로 검증한다.
